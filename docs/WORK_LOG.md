## 1. Org performance (29 Sep 2026)

Goal: reduce load times with no loss of UI or functionality.

- Deactivated all 51 `SDO_Tool_SalesforceRewind_*` triggers on standard objects, so saves on Accounts, Leads, Opportunities, Cases and others no longer run them. To restore, set them Active and redeploy.
- `wdGlassRecord`: the record loads in parallel with the object description, which removes one server wait per page.
- `wdGlassRelated`: related-list data is requested as soon as the page opens.
- Activity card, Home, and the Leads / Inventory / Bookings tabs show cached data instantly and refresh behind it.
- Account page: three customer panels now share one server request.
- New `wdGlassPrefetch` component, generated by `scripts/generateWdGlassPrefetch.mjs`, holds precomputed field and related-list details.

## 2. Tower Explorer: stock and inventory selection (29 Sep 2026)

Built from a Claude artifact prototype ("Tower Studio").

- **Stock tab** shows Tower Explorer: pick a project, then a tower. It has counts, filters (BHK, status, floor range, budget) and a Status/Price colour switch. A unit opens a side panel with areas and price breakdown. The old `stockTab` component is kept for rollback.
- **Opportunity > Select Inventory** is a new button that opens the explorer in a wide popup.
  - Saving writes the unit to `Interested_Unit__c` and marks it Reserved.
  - A previously reserved unit goes back to Available, unless another open opportunity points to it.
  - If someone else took the unit first, an error shows and the statuses reload.
- Enabled `Reserved` on the Residential Unit record type, since tagging would otherwise fail.
- UI fixes: the project dropdown was painted under the filter panel, so the top bar was layered above it. The floor and budget filters became two-handle sliders.
- Demo data seeded by `scripts/seedVarthurVistaTower1.apex`.
- Known limits: the button is on the desktop page only, reserving is not sent to SAP, and price is the tower rate times area plus charges, before tax.

## 3. Email support agent review (29 Sep 2026)

Reviewed and tested `Nikoo_Homes_Email_Support_Agent`.

- Flow: Email-to-Case, then `ResiCaseClassifier` (COMPLEX or SIMPLE by keyword), then flow `Nikoo_Email_Agent_Reply`, then the agent, then `ResiAgentSendReply`.
- COMPLEX cases create a child case in the `Nikoo_CRM_Escalations` queue. Other cases are answered with actions such as booking details, payment status, documents and SOP search.
- Test case 00001409: the agent wrote the correct reply, but it was not emailed because the sandbox cannot send email. Nothing wrong with the agent itself.

## 7a. Co-applicant and nominee Contacts (20 Oct 2026)

- Pulled the latest booking form and `wdGlass` code from the org first. This included Prajwal's 14-16 Oct 2026 changes, which are committed separately.
- Submitting the booking form now creates one **Contact** per co-applicant and per nominee.
  - Each Contact links to the opportunity's account through a new **Customer Account** lookup. Salesforce does not allow Contacts under person accounts, so the standard `AccountId` is set only when the account is a business account.
  - New Contact fields: `Customer_Account__c`, `Booking_Opportunity__c`, `Booking_Role__c` (Co-Applicant / Nominee), `Relationship_to_Applicant__c`, and `Booking_Form_Key__c` (a unique key, so re-submitting updates the same Contacts).
  - People removed from the form are removed from the Contacts. A failure here never blocks the booking submission.
- The existing behaviour is unchanged: co-applicant person accounts, contact roles, the booking's Co_Applicant fields, and the nominee fields on the Opportunity.
- The Account 360 page has a "Co-applicants & nominees" card on the Overview & Units tab, shown only when such Contacts exist.
- New permission set **Nikoo Booking Contacts** gives access to the new fields. It is not assigned to anyone yet.
- Deployed to UAT. `BookingFormControllerTest` and `WdGlassCustomerControllerTest` pass 12/12.
